# 45. FP32 (32-bit Floating Point)

**Stage:** 2 | **Priority:** Must know | **Prerequisites:** [Numerical Precision Basics](44_Numerical_Precision_Basics.md)

## In one sentence
FP32 is standard single-precision floating point (1 sign, 8 exponent, 23 mantissa bits) — high precision, 4 bytes per number, rarely the right choice for LLM inference weights.

## Plain-English explanation
FP32 is the "normal" float most programmers know. It's accurate and has a huge range, but it doubles memory and bandwidth compared to 16-bit formats. For a 9B model, FP32 weights would be ~36 GB — nearly the whole A100 — leaving almost nothing for cache.

## Technical depth
- Range ~1e-38 to ~3e38; ~7 decimal digits of precision.
- A100 FP32 on CUDA cores: ~19.5 TFLOPS. With **TF32** Tensor Core mode (FP32 inputs truncated to 10-bit mantissa internally): ~156 TFLOPS.
- Still used inside inference for: **accumulators** in matmuls, softmax/normalization reductions, some recurrent state updates (SSM/delta-rule state may be kept in FP32 for stability), and sampling.
- Mamba-style models sometimes keep the recurrent state or certain parameters (like `A_log`, `dt`) in FP32 — check config/engine options for state dtype.

## Backend-engineer analogy
Like storing every number as a 64-bit double "just in case" — correct, but wasteful for bandwidth-bound workloads.

## Why it matters for GreenMind
You won't serve weights in FP32, but you should know where FP32 still appears internally — especially recurrent state precision in hybrid models, which affects memory per sequence.

## Common mistakes
- Assuming FP32 is the "safest" default for inference — it's usually just slower with negligible quality gain over BF16.
