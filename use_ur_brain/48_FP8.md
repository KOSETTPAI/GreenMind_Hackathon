# 48. FP8 (8-bit Floating Point)

**Stage:** 2 / 7 | **Priority:** Should know | **Prerequisites:** [FP16](47_FP16.md)

## In one sentence
FP8 is a family of 8-bit float formats (E4M3 and E5M2) that halves memory vs BF16, but needs per-tensor/channel scaling — and the A100 has no native FP8 Tensor Core support.

## Plain-English explanation
With only 8 bits, you can't represent the full range of weights directly, so each tensor (or channel/block) carries a **scale** factor. E4M3 has more precision (used for weights/activations); E5M2 has more range (often used for gradients).

On Hopper/Ada GPUs, FP8 doubles Tensor Core throughput vs BF16. On the **A100**, FP8 is mainly a **storage format**: weights are stored in FP8 and dequantized to 16-bit inside the kernel (weight-only, "W8A16"), saving memory and bandwidth but not giving FP8 compute.

## Technical depth
- E4M3: 1/4/3, max ≈ 448. E5M2: 1/5/2, max ≈ 57,344.
- Scaling granularity: per-tensor, per-channel, per-block (e.g., 128×128). Finer = more accurate, more metadata.
- vLLM supports FP8 checkpoints on Ampere via weight-only Marlin-style kernels; FP8 activation quantization and FP8 KV cache behave differently on sm_80 — check the docs for your installed vLLM version.
- **FP8 KV cache** (`--kv-cache-dtype fp8`) halves attention cache memory; accuracy impact must be measured; support on A100 and for hybrid models must be verified.

## Backend-engineer analogy
A compact encoding with a per-block dictionary/scale — like delta or dictionary compression that must be decoded before use.

## Why it matters for GreenMind
An FP8 weight-only checkpoint could cut weight memory/bandwidth ~2× with typically small accuracy loss — but don't expect H100-style compute gains on A100.

## Common mistakes
- Copying H100 FP8 benchmarks as expectations for A100.
- Assuming FP8 KV cache is supported for every layer type in a hybrid model.
